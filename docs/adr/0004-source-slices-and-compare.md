# ADR 0004：允许按源切片与端对比，但只能有一份 Dataset 和一套聚合

- 状态：已采纳
- 日期：2026-10-29
- 相关：`docs/adr/0003-merge-workbuddy-into-one-dataset.md`（本 ADR 修订其决策 1）、`docs/workbuddy-data-sources.md` §9、`GLOSSARY.md`

## 背景

ADR 0003 裁定「`source` 只用于追溯与体检，**不作为统计维度**，UI 不提供只看某一源的切换」，前提是用户只想要「一份总账」。

新的用户需求改变了前提：

1. 只传入 CodeBuddy、只传入 WorkBuddy、两端都传入，三种情况都要能用；
2. 两端都传入时合并统计，同时要能看出**两端的消耗差异**。

不加区分地按 0003 执行会得到两个坏结果之一：要么拒绝需求，要么在实现里偷偷为某一端写第二条统计路径——后者正是 0003 否决的东西。

实测事实（`docs/workbuddy-data-sources.md` §9.2，勿推翻）：

- 两源 token 用量**零重叠**，合并就是相加，不需要跨源去重；
- 两源项目交集只有 1 个（`ylts-web`），差异只在分隔符；
- 模型的「未记录」桶全部来自 CodeBuddy 缺失 `selectedModelId` 的会话；
- 积分共用同一账户，单源 `Σcredit` 只是该端记到的部分。

## 决策

**1. 一份 Dataset，多一个受限维度。**

`SessionRecord.source` 与 `RequestRecord.model` 进入契约；`Dataset.bySource` 保存逐源溯源与自检。统计仍然只有一份 `Dataset`，`aggregate(dataset, win, { source })` 只是**同一函数上的过滤参数**。

明确禁止：为某一端新增 `aggregateWorkbuddy()`、第二份 Dataset 结构、或第二套指标定义。所有视图（合并 / 单源 / 端对比）必须由同一个 `aggregate()` 算出，端对比卡只做展示，不做二次计算。

**2. 三种输入模式共用一个入口，按文件形状识别源。**

用户不需要声明「我要看哪个产品」。识别规则：

- 路径含 `history` 且文件名 `index.json` → CodeBuddy；
- `…/projects/<目录>/<id>.jsonl` 或 `…/<id>/subagents/*.jsonl` → WorkBuddy；
- `codebuddy-sessions.vscdb` → CodeBuddy 元数据。

一次拖入同时命中两种形状时产出两个切片；后拖的一端只替换自己那一端，不重扫另一端。

**3. 「端差异」限定为三个可比层面。**

- **量差**：token / 请求 / 活跃天 / 会话（主会话与 subagent 分列）；
- **效率差**：只认**跨源同名模型**的命中率与每百万 token 积分——跨模型的「每百万 token 积分」主要反映模型构成，不是端效率；
- **节奏差**：逐日「只用 A / 只用 B / 都用 / 都没用」的分布。

**比率字段一律重算，禁止相加或取平均**（命中率、单次均值、每百万 token 积分、份额、覆盖率）。

**4. 会话数必须分列主会话与 subagent。**

WorkBuddy 的 subagent 会话独立存在（实测 70+ 个）。与 CodeBuddy 的「会话」直接相加会得出「WorkBuddy 会话更多」的错误结论。

**5. 同源重复输入是替换，不是累加。**

先扫 WorkBuddy、再导入一份旧的 WorkBuddy 快照，必须替换原切片并提示；跨源绝不互相去重。

**6. 积分文案按视图分层。**

- 单源视图：**「该端已知积分（覆盖 X% 请求）」**；
- 合并视图：**「已知积分」/「账号消耗下限」**；
- 任何视图都不得出现「总积分」，不得按比例外推。

## 考虑过的替代方案

- **两个独立看板 + 顶栏源开关**：仍被否。它会把「同一项目的两端用量」永久拆开，也让合并口径无法复用。
- **只做合并视图，差异用一句百分比带过**：被否。看不出效率差异，等于没回答需求。
- **端差异直接对比 `Σcredit`**：被否。两端字段覆盖率不同（WorkBuddy 94.5%，CodeBuddy 的 ask 模式恒为 0），必须带覆盖率才能比。
- **用项目目录名（cwd 末段）配对两端项目**：仍被否（0003）：`D:/a/util` 与 `D:/b/util` 会误并。

## 后果

- 正向：三种输入模式都成立；端差异与总账共用一套口径，可用单测断言 `合并 == Σ切片`；「只看某一端」退化为临时筛选，不产生第二套数字。
- 代价：`aggregate` 多一次线性扫描（12k 请求量级，可忽略）；`ModelStat.sessions` 改为「窗口内出现过该模型的会话数」，语义比"会话级归属"更弱，必须在文案上说清。
- 约束：任何新增指标都要先回答「它属于量差、效率差还是节奏差」，否则不进端对比卡。
- 未决：`workbuddy.db` 的标题/真实 cwd 仍未接入（见 0003 决策 5）；接入后只影响覆盖率，不改变本 ADR 的结构。
